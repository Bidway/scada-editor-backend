# Изменения контракта: таблицы и наборы значений

Дата: 30.07.2026. Ветка бэкенда: `microservice`.

Таблица в редакторе перестала быть «таблицей рецептов»: тем же механизмом описываются параметры
станции и любые другие именованные наборы значений. Заодно закрыты две дыры: строки без тега
(локальные параметры) раньше не могли попасть в набор вообще, а порядок строк не был определён.

Ниже — всё, что меняется на стороне фронта. **Ломающих изменений три**: `row_name` вместо
`tag_id` в значениях набора, новая форма ответа `/resolved`, `sessionId` в применении.

---

## 1. Строки таблицы — новое поле `position`

`PropertyCreateDto` / `PropertyResponseDto` получили `position` (целое, может быть `null`).

```json
{
  "id": 51,
  "name": "Уставка локальная",
  "component_id": 982,
  "property_type": "Локальный",
  "tag_id": null,
  "value_type": "number",
  "default_value": "0",
  "position": 0,
  "logging": false,
  "onChange": null
}
```

**Что важно:**

- `position` — **только для представления**: номер в первой колонке и порядок строк. Ключом
  ничего не является, привязка значений идёт по имени строки (см. п. 2).
- Присылать его не обязательно. При сохранении компонента с `properties[]` сервер проставит
  `position` по порядку элементов массива. Пришлёте своё значение — сервер возьмёт его.
- В дереве проекта свойства теперь приходят отсортированными: по `position`, затем по `id`.
  Свойства, созданные до этого изменения, имеют `position: null` и идут в конце.
- Номер в первой колонке можно рисовать и как позицию в списке (`index + 1`) — тогда после
  перестановки строк он пересчитается сам.

## 2. Имя строки стало ключом

Имя свойства (`name`) — это то, по чему значение набора находит свою строку. Отсюда два правила,
которые бэкенд теперь проверяет:

- **Имена уникальны в пределах компонента.** Дубликат → `400` с сообщением
  `Duplicate property name '<имя>' in component <id>; names must be unique within a component`.
  Лучше проверять в UI до отправки.
- **Пробелы по краям срезаются** при сохранении: `"  Насос 1  "` сохранится как `"Насос 1"`.
  Учтите при сравнении на клиенте.

### Переименование строки — только точечным вызовом

```
PUT /api/editor/properties/{id}      заголовок X-Username обязателен
```

Только этот вызов переносит значения во всех наборах таблицы на новое имя. При сохранении
компонента целиком (`PUT /api/editor/components` с `properties[]`) переименование неотличимо от
«одну строку удалили, другую добавили» — значения за ним не поедут и останутся привязанными к
старому имени.

**Если пользователь правит название строки в таблице — отправляйте `PUT /properties/{id}`, а не
пересохранение всей таблицы.**

## 3. Наборы значений: `row_name` вместо `tag_id`, новое поле `type`

`POST /api/editor/recipes`, `PUT /api/editor/recipes/{id}`

**Было:**
```json
{
  "name": "Продукт-A",
  "component_id": 982,
  "values": [ { "tag_id": "Барановичи-1.BN1_MCA1...ST", "value": "true" } ]
}
```

**Стало:**
```json
{
  "name": "Продукт-A",
  "type": "recipe",
  "component_id": 982,
  "values": [
    { "row_name": "Клапан 1",         "value": "true" },
    { "row_name": "Наполнение танка", "value": "77.5" },
    { "row_name": "Уставка локальная","value": "7"    }
  ]
}
```

- `row_name` — имя строки таблицы. Обязательно; пустое → `400`.
- `type` — вид набора. Не прислан → `"recipe"`. Известные значения: `recipe` (уставки под
  продукт), `station_params` (параметры станции). Список открытый: любое своё значение бэкенд
  примет, фильтровать наборы по нему можно на клиенте.
- Строки **без тега** (локальные параметры) теперь тоже могут входить в набор — раньше они
  просто игнорировались.

`GET /api/editor/recipes?componentId=982` и `GET /api/editor/recipes/{id}` отдают ту же
структуру плюс `id`.

## 4. `GET /api/editor/recipes/{id}/resolved` — теперь объект, а не массив

**Было:** `[ { "tag_id": "...", "value": "...", "value_type": "..." } ]`

**Стало:**
```json
{
  "recipe_id": 4,
  "component_id": 982,
  "values": [
    { "row_name": "Клапан 1",          "value": "true", "value_type": "bool",   "tag_id": "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V10.ST" },
    { "row_name": "Наполнение танка",  "value": "77.5", "value_type": "number", "tag_id": "Барановичи-1.BN1_MCA1.V_M_1.LINE1V0.M" },
    { "row_name": "Уставка локальная", "value": "7",    "value_type": "number", "tag_id": null }
  ],
  "unmatched_rows": ["Строки нет"]
}
```

- `tag_id: null` — локальная строка: значение не пойдёт в ПЛК, а ляжет в состояние сессии.
- `unmatched_rows` — имена строк, которых в таблице больше нет (строку удалили или переименовали
  в обход `PUT /properties/{id}`). Их значения применить не к чему. Это удобное место, чтобы
  показать оператору «набор частично устарел» до того, как он нажмёт «Применить».

Эндпоинт использует runtime, но фронту он полезен для предпросмотра.

## 5. `POST /api/runtime/recipes/apply` — добавился `sessionId`

**Запрос:**
```json
{ "recipeId": 4, "sessionId": "c3469902-2a9c-4d70-a8b2-ed59b097fcbf", "projectId": 980 }
```

`sessionId` — та самая сессия мониторинга, что вернул `POST /api/runtime/sessions`. Нужен только
для локальных строк: их значение живёт в сессии, а не в ПЛК. Без него теговые строки применятся,
а локальные попадут в `failedRows`. **Если в таблице есть строки без тега — присылайте
`sessionId` всегда.**

**Ответ (изменился):**
```json
{
  "recipeId": 4,
  "total": 3,
  "sent": 2,
  "localApplied": 1,
  "failed": 0,
  "failedRows": [],
  "unmatchedRows": ["Строки нет"]
}
```

Было `{recipeId, total, sent, failed, failedTags}`. Стало: `sent` — сколько ушло в ПЛК,
`localApplied` — сколько записано в сессию, `failedRows` / `unmatchedRows` — имена строк
(раньше был `failedTags` с тегами).

## 6. WebSocket — новых каналов нет

Значения локальных строк приходят в уже существующем поле `properties[]` кадра `UPDATE`:

```json
{
  "type": "UPDATE",
  "tags": [ { "tagId": "...", "value": "true", "ts": 1785419415010 } ],
  "properties": [ { "propertyId": 51, "propertyName": "Уставка локальная", "value": 7.0, "ts": 1785419415007 } ]
}
```

Сопоставлять строку таблицы удобнее по `propertyName` (он же `row_name` набора): `propertyId`
пересоздаётся при каждом пересохранении таблицы в редакторе.

Значения теговых строк, как и раньше, приходят в `tags[]` по `tagId`.

Отдельно: `GET /api/runtime/sessions/{id}/snapshot?componentId={id}` возвращает **только теговые**
строки — у локальных нет тега, их текущее значение берётся из `properties[]` (или из
`default_value` до первого изменения).

---

## Что сделать на фронте — чек-лист

1. В редакторе таблицы отправлять `properties[]` в нужном порядке; `position` можно не слать.
2. Номер строки не использовать как идентификатор — только для показа.
3. Валидировать уникальность имён строк в пределах таблицы до сохранения.
4. Переименование строки — `PUT /api/editor/properties/{id}` (заголовок `X-Username`), не
   пересохранение таблицы.
5. В наборах заменить `tag_id` на `row_name`; при желании использовать `type` для разделения
   рецептов и параметров станции в UI.
6. `/resolved` читать как объект; показывать `unmatched_rows` как предупреждение.
7. В `apply` передавать `sessionId`; в ответе разбирать `sent` / `localApplied` /
   `failedRows` / `unmatchedRows`.
8. Значения из `properties[]` по WS применять к строкам таблицы, сопоставляя по `propertyName`.

## Про данные

Ранее существовавшие наборы (2 шт. на стенде) были тестовыми и удалены при переходе на новый
ключ. Таблицы, строки и всё остальное не тронуты.
