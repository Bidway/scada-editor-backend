# Связь фронт ↔ runtime: каналы, сообщения, что доделать

> Документ для команды фронтенда (`scada-editor-frontend`) и для владельца бэка.
> Актуально на 22.07.2026. Контракт выверен по коду `runtime` (сервис `:8085`) и
> по фактическим сообщениям на проводе.

## TL;DR

- **Модель тега — только строка.** Тег идентифицируется путём узла через точку
  (`idNode`, он же `ComponentProperty.tag_id`, он же Kafka-key телеметрии). Никаких
  числовых id тега в контракте нет.
- **Два канала.** (1) HTTP — разово создать сессию мониторинга и получить дерево
  проекта; (2) WebSocket — живые значения тегов вниз и команды (нажатия) вверх.
- **Что фронт отправляет:** `POST /api/runtime/sessions` (создать сессию) и по WS —
  `{"type":"ACTION","scriptId":N}` (запустить серверный скрипт, напр. «открыть клапан»)
  + `{"type":"PING"}` (keepalive).
- **Что фронт получает:** ответ сессии `{sessionId, wsPath, projectTree}` и по WS —
  `{"type":"UPDATE","tags":[…],"properties":[…]}` (значения тегов и записи серверных
  скриптов в свойства).
- **Что нужно доделать на фронте:** оживить `sendAction` — связать клик кнопки с
  серверным скриптом (см. раздел «Что реализовать»). Остальные каналы уже работают.

## Общая схема

```
                    ┌─────────────── HTTP (через gateway :8080, Bearer) ───────────────┐
                    │  POST /api/runtime/sessions {projectId}                           │
   ФРОНТ (BFF)  ────┤     → {sessionId, wsPath, projectTree}                            ├──► runtime :8085
   Next.js route    └──────────────────────────────────────────────────────────────────┘
                    ┌─────────── WebSocket (НАПРЯМУЮ на runtime :8085, raw WS) ──────────┐
   ФРОНТ (браузер)  │  вверх:  {"type":"ACTION","scriptId":N}   {"type":"PING"}          │
                    │  вниз:   {"type":"UPDATE","tags":[…],"properties":[…]}             │◄─► runtime :8085
                    └───────────────────────────────────────────────────────────────────┘
```

Оба транспорта идут **через gateway** — он единственный опубликованный порт и единственное
место, где проверяется подпись токена:
- REST — заголовок `Authorization: Bearer <jwt>`;
- WebSocket — токен в query (`?token=<jwt>`), потому что браузер не умеет слать заголовок
  на апгрейде. Базовый origin — `NEXT_PUBLIC_RUNTIME_WS_URL`, теперь `ws://localhost:8080`.

## Канал 1 — HTTP: создание сессии

Разовый вызов при входе в режим монитора. Возвращает всё дерево проекта сразу
(компоненты, свойства, скрипты, привязки, состояния) — дальше живут только апдейты по WS.

### Запрос

```
POST /api/runtime/sessions          (фронтовый BFF → gateway → runtime)
Content-Type: application/json
Authorization: Bearer <jwt>          (нужен только на этом шаге, добавляет BFF)

{ "projectId": 950 }                 // id корневого компонента-проекта в editor
```

### Ответ `200 OK`

```json
{
  "sessionId": "d076fb45-0ed9-4799-ae43-b70900703dfd",
  "wsPath":    "/ws/runtime/d076fb45-0ed9-4799-ae43-b70900703dfd",
  "projectTree": { … полное дерево проекта … }
}
```

- `400` — проект не найден / неверный запрос.
- Сессия **одноразовая**: каждый (пере)коннект начинается с нового `POST` (новый
  `sessionId`). Явный `DELETE` не нужен — закрытие WS завершает сессию на сервере.

### `projectTree` (рекурсивное дерево)

Каждый узел:

```jsonc
{
  "id": 962, "name": "Кнопка", "type": "...", "version": 1, "parent_id": 951,
  "states":     [ { "name": "...", "image": {…только графика…} } ],
  "children":   [ … такие же узлы … ],
  "properties": [ { "id": 24, "name": "ST", "property_type": "Тег",
                    "tag_id": "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST",
                    "default_value": "", "on_change": "…" } ],
  "scripts":    [ { "id": 13, "name": "Открыть клапан", "script": "writeTag('ST', true);" } ],
  "bindings":   [ … привязки отрисовки … ],
  "events":     [ { "id": 1, "event_type": "onClick", "script": "…" } ]
}
```

Для связи «клик → сервер» фронту важны три поля узла:
- **`events[]`** — обработчики событий компонента. Лежат на **уровне компонента**, а не
  внутри `states[].image` (переезд 23.07.2026): обработчик принадлежит компоненту, а не
  картинке состояния. `event_type` — `onClick`, `onDoubleClick`, `onMouseDown`, `onMouseUp`,
  `onHover`, `onHoverOut`, `onOpen`, `onClose`. Все исполняются на фронте.
- **`scripts[]`** — серверные скрипты компонента. `scripts[].id` — это и есть `scriptId`
  для `ACTION` (см. канал 2). На фронте это `ElementScript{ id, name, content }`.
- **`properties[].tag_id`** — путь тега (`idNode`); по нему приходят значения в `tags[]`.

`image` теперь хранит **только графику**: ключ `events` вычищается при сохранении
компонента, поэтому обработчик, записанный туда, молча пропадёт.

## Канал 2 — WebSocket: живые данные и команды

После ответа сессии фронт открывает raw WebSocket (НЕ SockJS/STOMP):

```
ws://localhost:8080 + wsPath + "?token=" + jwt
// напр. ws://localhost:8080/ws/runtime/<sessionId>?token=eyJhbGciOi...
```

### Фронт → сервер (что отправляем)

**1. Запуск серверного скрипта (нажатие кнопки, запись тега в ПЛК):**

```json
{ "type": "ACTION", "scriptId": 13 }
```

`scriptId` — числовой `id` из `projectTree … scripts[].id` того компонента, чей скрипт
запускаем. На фронте `ElementScript.id` — строка, поэтому передавать `Number(script.id)`.

**2. Keepalive:**

```json
{ "type": "PING" }
```

Heartbeat на сервере не реализован — фронт шлёт `PING` (напр. раз в 20 с). Сервер молча
игнорирует любой неизвестный тип — это ожидаемо и безопасно.

### Сервер → фронт (что получаем)

Единственный тип входящего сообщения — `UPDATE`:

```json
{
  "type": "UPDATE",
  "tags": [
    { "tagId": "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST", "value": "false", "ts": 1784696916495 }
  ],
  "properties": [
    { "propertyId": 25, "propertyName": "Состояние", "value": "Закрыт", "ts": 1784696916495 }
  ]
}
```

- **`tags[]`** — сырые значения тегов. `tagId` = путь узла (`idNode`), `value` — **всегда
  строка** (`"true"`, `"72.7"`), `ts` — epoch ms. Приходят батчами (сервер коалесирует
  ~40 мс). Маршрутизировать по `tagId`.
- **`properties[]`** — результаты серверных скриптов (`onChange` / `ACTION`), записанные
  в свойства компонентов. `propertyId` — числовой id свойства, `propertyName` — его имя,
  `value` — новое значение, `ts` — epoch ms. Маршрутизировать по `propertyId`.

**Важные нюансы приёма:**
- Ответ на `ACTION` приходит тем же `UPDATE`, но **`tags` = `null`** (не `[]`) —
  нормализация `tags ?? []` обязательна.
- Оба массива опциональны; батч может нести только `tags`, только `properties`, либо оба.
- Обрыв WS убивает сессию на сервере → переподключение **обязано** заново делать `POST`
  (новый `sessionId`), а не просто переоткрывать сокет.

## Что реализовать на фронте (единственный разрыв)

Всё выше уже работает, **кроме связи «клик кнопки → серверный скрипт»**. Функция
`sendAction(scriptId)` в `src/lib/runtime/runtimeConnection.ts` написана, но её **никто
не вызывает**: соединение `conn` создаётся внутри `useEffect` и не доходит до обработчика
клика.

### 3.0 (ломающее, 23.07.2026) — обработчики событий переехали из `image` в `events[]`

Раньше `onClick` лежал в `component_state.image.events` — jsonb графики каждого состояния.
Теперь это таблица `editor.component_event`, а в дереве — массив `events[]` **на уровне
компонента** (см. «`projectTree`» выше). Причина: обработчик принадлежит компоненту, а не
картинке; в старой схеме его приходилось дублировать в каждое состояние, и он затирался
при перерисовке фигуры.

Что сделать:

1. **Чтение.** Брать обработчик из `element.events`, а не из `state.image.events`.
   В типе элемента: `events: Array<{ id, event_type, script }>` вместо объекта-мапы.
   Резолв обработчика — поиск по `event_type` (`events.find(e => e.event_type === 'onClick')`).
2. **Сохранение.** В `buildComponentTree.ts` слать `events[]` рядом со `scripts[]`
   и `bindings[]`; из `image` ключ `events` убрать (бэк его всё равно вычищает).
3. **Редактор.** Панель событий переезжает из свойств состояния в свойства компонента.

Формат на запись — тот же, без `id`:

```jsonc
"events": [ { "event_type": "onClick", "script": "runScript('Открыть клапан');" } ]
```

Допустимые `event_type`: `onClick`, `onDoubleClick`, `onMouseDown`, `onMouseUp`,
`onHover`, `onHoverOut`, `onOpen`, `onClose`. Прочее — `400`. Ещё две ошибки `400`:
два обработчика с одинаковым `event_type` у компонента и пустой `script` (чтобы удалить
обработчик — не присылайте его вовсе).

> **Осторожно с `PUT /api/editor/components`.** Он синхронизирует коллекции целиком:
> `states`, `scripts`, `bindings`, `events` **заменяются** содержимым DTO, а отсутствующее
> поле означает пустой список. Частичный `PUT` (например, только с `events`) сотрёт
> состояния и скрипты компонента. Сохранять всегда полным узлом.

### 3.1 (обязательно) — оживить `sendAction`

Клик по фигуре в мониторе уже доходит до `useRuntimeEngine.runEvent`, где исполняется
фронтовый обработчик `onClick` элемента. Нужно дать этому обработчику способ позвать бэк:

1. В `useRuntimeEngine.ts` держать `conn` в `connRef` (сейчас он локальная константа
   в `useEffect` создания соединения).
2. В `src/lib/runtime/eventScript.ts` добавить в песочницу обработчика функцию
   `runScript(name)`: `compileEventScript` — дописать `"runScript"` в параметры
   `new Function(...)`; `executeEventScript` — принять колбэк и передать его в вызов.
3. Колбэк `runScript(name)` в `runEvent`: найти в `el.scripts` скрипт с таким `name`
   и вызвать `connRef.current.sendAction(Number(script.id))`.
4. Внести `runScript` в `RESERVED_WORDS` (`bindingScope.ts`), чтобы свойство с таким
   именем не затеняло функцию.

После этого обработчик `onClick` кнопки становится, например:

```js
runScript("Открыть клапан");   // → WS ACTION → серверный скрипт → команда в ПЛК
```

### 3.2 (для прогресс-бара) — сырое значение тега в буфер свойств

Прогресс-бар своих свойств не имеет и ссылается на свойство `fullness` через
`propertyRefs`, т.е. читает буфер свойств по `propertyId`. Но сырое значение тега
приходит по `tagId`. Нужно: в `bindingIndex.ts` построить `tag_id → propertyId[]` из
`el.properties` (там есть и `id`, и `tag_id`) и в `flush` при изменении тега писать
значение и в буфер свойств. Чинит `direct`-привязки и прогресс-бар.

### 3.3 (устойчивость сейва) — не ронять сохранение сцены

Бэк требует, чтобы `bindings[].component_property_id` ссылался на существующее свойство
**этого же** компонента; иначе сейв всей сцены падает `400`. UI это уже подсвечивает, но
в `encodeBindings` (`buildComponentTree.ts`) такие привязки надо пропускать с
`console.warn`, а не валить всё сохранение.

### 3.4 — привязки сцены (чистая отрисовка, заводятся в редакторе)

- Клапан2: `if (ST.V === true) setState("Нормальное"); else setState("Закрыт")`
- Клапан1: то же на «Нормальное»/«Зактрыто» (имена состояний в БД именно такие)
- Прогресс-бар: `direct`-привязка на `fullness` через `propertyRefs`

## Разграничение ответственности фронт/бэк

Правило: **влияет на объект или на общее состояние — бэк; только рисует — фронт.**

| Задача | Слой | Механизм | Триггер |
|---|---|---|---|
| Запись тега / команда в ПЛК | **бэк** | серверный `Script` → `writeTag()` | `ACTION` по WS |
| Производное состояние, единое для всех операторов | **бэк** | `onChange` свойства → `PROPERTY_UPDATE` всем | смена привязанного тега |
| Отрисовка (цвет, текст, размер, прогресс) | **фронт** | `Binding.script` — локально у оператора | значения из `UPDATE` |
| Реакция на клик оператора | **фронт → бэк** | `events[]` (`event_type: onClick`); пишет тег → `runScript` → `ACTION` | клик |

Почему так: серверный скрипт исполняется один раз на весь стенд (консистентно и
безопасно), фронтовый — у каждого оператора (бесплатно для сервера, но недоверенно и
локально). Запись тега и общее состояние обязаны быть одинаковыми у всех → бэк; чистая
отрисовка у каждого своя → фронт. `writeTag` доступен **только** в серверном скрипте — в
песочнице фронтового обработчика его нет (там лишь `setProperty/setProp/setState`).

## Полный сценарий: нажали кнопку «Открыть клапан»

```
1. Оператор кликает кнопку в мониторе.
2. Фронт: runEvent → onClick → runScript("Открыть клапан")
        → conn.sendAction(13)
        → WS: {"type":"ACTION","scriptId":13}
3. Бэк (runtime): handleAction(13)
        → исполняет серверный Script: writeTag('ST', true)
        → резолв: свойство 'ST' кнопки → idNode "…V_ST_1.LINE1V0.ST"
        → публикует команду в Kafka (топик команд):
             { "commandId":"…", "idNode":"…V_ST_1.LINE1V0.ST",
               "value":true, "dataType":"BOOLEAN", … }
        → драйвер устройства пишет значение в контроллер (OPC UA или Modbus — по idNode)
4. Обратная связь оператору:
        - если Script менял свойства — сразу приходит UPDATE с properties[]
          (ответ на ACTION: tags=null);
        - когда тег реально изменится, телеметрия придёт в tags[], а onChange
          свойства обновит производные свойства (напр. «Состояние») всем операторам.
5. Фронт: onUpdate → буферы → flush (5 Гц) → биндинги → перерисовка сцены.
```

Фронт при этом знает только про HTTP+WS; Kafka и протокол ПЛК — забота бэка. Со стороны
фронта команда — это ровно одно WS-сообщение `{"type":"ACTION","scriptId":N}`.

## Быстрый чек-лист для фронта

- [ ] `POST /api/runtime/sessions {projectId}` → взять `wsPath`, отрисовать `projectTree`.
- [ ] Открыть raw WS на `NEXT_PUBLIC_RUNTIME_WS_URL + wsPath + "?token=" + jwt`
      (через gateway, `ws://localhost:8080`).
- [ ] Принимать `UPDATE`: `tags ?? []`, `properties ?? []`; маршрут по `tagId` / `propertyId`.
- [ ] Слать `PING` раз в ~20 с; на `onclose` — заново `POST` (новый sessionId).
- [ ] **Реализовать `runScript` → `sendAction(Number(script.id))`** (раздел 3.1).
- [ ] Значения тегов — строки; приводить типы при отрисовке.
