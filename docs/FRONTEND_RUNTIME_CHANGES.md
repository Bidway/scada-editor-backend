# Изменения контракта: runtime (мониторинг, WS, применение наборов)

Дата: 31.07.2026. Ветка бэкенда: `microservice`. Коммиты: `28c3bd0`, `c42a860`, `af1e1bf`,
`cb983c3`, `310b4aa`, `4d0363f`, `497aea6`.

Правки закрыли два дефекта записи в ПЛК и распараллелили путь телеметрии
(Kafka → скрипты → WebSocket). **Формат JSON нигде не изменился** — изменились тайминги,
наполнение полей и допущения, на которых можно строить клиент.

Ломающих изменений четыре:

1. `POST /api/runtime/recipes/apply` отвечает медленнее — нужен таймаут ≥ 15 с (п. 1).
2. `failed` / `failedRows` перестали быть всегда пустыми — нужен UI частичного успеха (п. 2).
3. Булева уставка вне списка написаний больше не пишется в ПЛК — нужна валидация в редакторе (п. 3).
4. WS-кадр больше не «одно изменение»: дубли `tagId` внутри кадра, склейка кадров,
   `properties` отстают от `tags` (п. 4–6).

---

## 1. `POST /api/runtime/recipes/apply` отвечает после подтверждения брокера

**Было:** ответ приходил сразу, как команды легли в буфер продюсера Kafka. Оператор видел
`sent: 12, failed: 0` даже когда брокер был недоступен и в ПЛК не ушло ничего.

**Стало:** сервис ждёт подтверждения по всем отправленным командам, общий дедлайн — 7 с
(`RecipeApplyService.ACK_TIMEOUT_MS`), плюс время резолва набора в editor.

Что делать:

- **Таймаут HTTP-клиента — не меньше 15 с** на этом запросе. Дефолтные 5–10 с в axios/ky/fetch-обёртке
  дадут сетевую ошибку на успешно применённом рецепте. Прокси перед фронтом (nginx, Next.js
  rewrites) — тоже.
- **Блокировать кнопку до ответа.** Повторное нажатие применяет уставки в ПЛК второй раз.
  Идемпотентности на бэкенде нет.
- Показывать прогресс: 7 секунд без обратной связи оператор воспримет как зависание.

```ts
const res = await fetch(`${API}/api/runtime/recipes/apply`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ recipeId, sessionId, projectId }),
  signal: AbortSignal.timeout(20_000),   // ← было 5_000
});
```

**`sessionId` передавать всегда.** Без него строки без тега (локальные параметры) применить некуда,
и они молча уйдут в `failedRows`.

## 2. Отчёт о применении: частичный успех — штатный исход

Форма ответа прежняя, наполнение — новое.

```json
{
  "recipeId": 17,
  "total": 12,
  "sent": 9,
  "localApplied": 1,
  "failed": 2,
  "failedRows": ["Уставка давления", "Клапан подачи"],
  "unmatchedRows": ["Старая строка"]
}
```

| Поле | Что означает |
|---|---|
| `total` | сколько значений было в наборе после резолва |
| `sent` | команд **подтверждено брокером** (раньше — «положено в буфер») |
| `localApplied` | локальных строк записано в состояние сессии |
| `failed` | `failedRows.length` |
| `failedRows` | имена строк (`name` свойства), которые не применились |
| `unmatchedRows` | строки набора, которых больше нет в таблице — применять не к чему |

В `failedRows` попадает три разных случая: брокер не подтвердил команду, значение не прошло разбор
(п. 3), локальная строка при отсутствующей сессии.

Что делать: статус считать по трём состояниям, а не по двум.

```ts
const status =
  r.failed === 0 && r.unmatchedRows.length === 0 ? 'ok'
  : r.sent + r.localApplied === 0                 ? 'error'
  : 'partial';
```

`partial` — это красный/жёлтый экран со списком `failedRows`, а не галочка. Оператор должен видеть,
**какие именно** уставки не доехали: часть механизма работает по новому рецепту, часть по старому.

## 3. Булевы уставки — только явные написания

**Было:** `Boolean.valueOf(raw)` — всё, кроме строки `"true"`, превращалось в `false`. Значение
`"1"`, `"да"`, `"on"` уходило в дискретный тег (клапан, пуск/стоп) как **противоположное**, без
единого признака ошибки.

**Стало** (`RecipeApplyService.parseBoolean`), для строк с `value_type` = `bool` / `boolean`:

| Результат | Принимаемые значения |
|---|---|
| `true` | `true`, `1`, `on`, `yes`, `да` |
| `false` | `false`, `0`, `off`, `no`, `нет` |

Регистр не важен, пробелы по краям срезаются. **Любое другое значение — ошибка строки:** в ПЛК
по ней не уходит ничего, имя попадает в `failedRows`, остальные строки набора применяются как обычно.

Что делать в редакторе таблиц/наборов:

- Для строки с `value_type` = `bool`/`boolean` — **чекбокс или селект**, не свободный ввод.
  Отправлять канонические `"true"` / `"false"`.
- Провалидировать существующие данные: значения вида `"Да"`, `"вкл"`, `"1 "` раньше «работали»
  (молча как `false`), теперь дадут ошибку применения.
- `value_type` на бэкенде — свободная строка без валидации (известный долг, пункт A8 аудита).
  Опечатка `"integr"` или `"Число"` не будет ошибкой, значение просто уйдёт строкой. Фронту стоит
  ограничить набор значений селектом: `number`, `int`, `bool`, `string`.

## 4. WS-кадр: один `tagId` может встретиться несколько раз

Контракт сообщения не изменился:

```json
{
  "type": "UPDATE",
  "tags":       [ { "tagId": "ns=2;s=P1.Flow", "value": "12.4", "ts": 1753960001234 } ],
  "properties": [ { "propertyId": 51, "propertyName": "Расход", "value": 12.4, "ts": 1753960001234 } ]
}
```

Изменился характер потока: `max-poll-records` подняли до 2000, чтение топика распараллелено,
а буфер сессии (`SessionOutboundBuffer`) — обычная очередь **без схлопывания по тегу**.
В одном кадре тег может встретиться сколько угодно раз с разными значениями.

Что делать:

- Применять массив **строго по порядку**, последнее значение выигрывает. Не сортировать, не
  собирать в `Map` параллельно (`Promise.all`, `forEach` с async), не дедуплицировать по `tagId`
  до применения.
- Кадр может быть большим (тысячи записей). Обновление стейта — одним батчем на кадр, не по одному
  `setState` на запись.

```ts
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  setTags(prev => {
    const next = new Map(prev);
    for (const t of msg.tags ?? []) next.set(t.tagId, t);        // порядок массива = порядок событий
    return next;
  });
  setProps(prev => {
    const next = new Map(prev);
    for (const p of msg.properties ?? []) next.set(p.propertyId, p);
    return next;
  });
};
```

`tags` и `properties` — каждый может отсутствовать или быть пустым. Ответ на `ACTION` приходит
только с `properties`.

Типы значений разные: `TagUpdate.value` — **всегда строка**, `PropertyUpdate.value` — произвольный
тип (число, строка, boolean, `null`), таким его вернул скрипт.

## 5. Промежуточные значения не гарантированы

Флашер отправляет кадр раз в 40 мс. Если предыдущая отправка этой сессии ещё идёт (медленный
клиент: VPN, спящий ноутбук), тик пропускается — данные остаются в буфере и уедут следующим,
более крупным кадром. При устойчивом отставании буфер ограничен 10 000 записей на вид, дальше
отбрасываются самые старые.

Что делать:

- Не строить тренды, графики и счётчики по принципу «каждый кадр = каждое изменение».
  Для истории нужен отдельный источник, поток WS для этого не предназначен.
- Анимации/интерполяцию не привязывать к частоте кадров.

## 6. `properties` отстают от `tags`

onChange-скрипты ушли с треда Kafka-consumer'а в отдельный пул (`OnChangeDispatcher`). Значение тега
и пересчитанное скриптом свойство теперь могут приехать **разными кадрами** — атомарности
«тег и его свойства в одном кадре» больше нет.

Что делать:

- Не ждать, что после прихода тега свойства компонента в том же кадре уже пересчитаны.
  Рендерить по последнему известному состоянию каждого источника отдельно.
- При перегрузке очередь полосы (по умолчанию 1000 задач) отбрасывает задачи — обновление свойства
  может не прийти вовсе. UI не должен блокироваться в ожидании.

Порядок внутри одной сессии сохраняется: сессия закреплена за полосой, её скрипты идут
последовательно.

## 7. WebSocket: одна сессия — одно соединение

`RuntimeWebSocketHandler` отклоняет второе подключение к той же сессии.

| Ситуация | Код закрытия | `reason` |
|---|---|---|
| У сессии уже есть живой WS | `1003` | `Session already has an active connection` |
| Сессии не существует / уже закрыта | `1003` | `Unknown runtime session` |
| Токен не передан или невалиден | `1006` (401 на апгрейде) | пусто |

Что делать:

- **По коду `1003` не переподключаться.** Это отказ по существу, реконнект-цикл будет крутиться
  вечно. Реконнект — только на `1006` / `1001`.
- При реконнекте сначала закрыть старый сокет и дождаться `onclose`, только потом открывать новый.
- **React StrictMode в dev монтирует эффекты дважды** — второй сокет получит `1003`, и это выглядит
  как «WS не работает». Нужен guard на уровне рефа/синглтона.

```ts
ws.onclose = (e) => {
  if (e.code === 1003) { showError(e.reason); return; }   // не реконнектить
  scheduleReconnect();
};
```

## 8. Токен на WebSocket

Проверка JWT на handshake включена по умолчанию (`runtime.ws.require-auth: true`). Браузерный
WebSocket не умеет слать `Authorization`, поэтому токен — в query:

```
ws://localhost:8085/ws/runtime/{sessionId}?token=<jwt>
```

Особенности, которые надо заложить в клиент:

- Отказ handshake виден браузеру только как `onerror` + close `1006` без причины. Отличить
  «токен протух» от «сети нет» на клиенте нельзя — **перед реконнектом обновлять токен**, а не
  переподключаться со старым.
- Токен живёт 1 час, refresh-токенов на бэкенде пока нет. Установленное соединение переживёт
  истечение (проверка только на handshake), но реконнект после разрыва упадёт. Для смены длиннее
  часа нужен ре-логин перед реконнектом.
- Для локального стенда без токена бэкенд поднимается с `RUNTIME_WS_REQUIRE_AUTH=false`.

## 9. Что не изменилось, но стоит поправить

Не связано с этими коммитами — всплыло при разборе и относится к тому же экрану.

- **URL WebSocket собирать из `wsPath`.** `POST /api/runtime/sessions` возвращает
  `{ sessionId, wsPath, projectTree }`, где `wsPath` — относительный путь
  (`/ws/runtime/{sessionId}`). Origin брать из переменной окружения, путь — из ответа.
  Хардкод `ws://host:8085/ws/runtime/${id}` придётся переписывать после п. 10.
- **Индикация «значение протухло».** `ts` — момент приёма в runtime (не время из ПЛК). Kafka-консьюмер
  теперь переживает сбои, но переподключается с паузой 5 с и читает с конца топика: разрыв в данных
  возможен, и никакого признака кроме остановившегося `ts` у фронта нет. Замерший экран оператор
  считает актуальным — это опаснее явной ошибки. Стоит гасить/помечать значения старше N секунд.
- **`GET /api/runtime/sessions/{sessionId}/snapshot?componentId=N`** → `[{ tagId, value }]` читает
  значения из памяти runtime. Сразу после его рестарта вернёт `null` по всем тегам — показывать
  «нет данных», а не `0`.
- **Закрывать сессию явно** — `DELETE /api/runtime/sessions/{id}` при уходе с экрана. Брошенные
  сессии подбирает reaper, но до этого они продолжают получать значения тегов в буфер.

## 10. WebSocket переехал на gateway — **ломающее, одна строка**

Сделано. Порты 8081–8085 больше не публикуются наружу: единственный вход — gateway на 8080,
и он же единственное место, где проверяется подпись токена.

Для фронта меняется **только origin**, путь и протокол прежние:

```diff
- ws://localhost:8085/ws/runtime/{sessionId}?token=<jwt>
+ ws://localhost:8080/ws/runtime/{sessionId}?token=<jwt>
```

```diff
# .env
- NEXT_PUBLIC_RUNTIME_WS_URL=ws://localhost:8085
+ NEXT_PUBLIC_RUNTIME_WS_URL=ws://localhost:8080
```

STOMP канала — туда же: `ws://localhost:8082/ws` → `ws://localhost:8080/ws`. Токен на нём пока
не требуется (аутентификация STOMP — отдельный шаг, B7), но порт 8082 снаружи уже недоступен.

Что важно знать:

- **`?token=` теперь обязателен именно на gateway.** Без него апгрейд получает `401` ещё
  до runtime. Битый или протухший токен — тот же `401`.
- Коды закрытия сквозные: `1003` из runtime (п. 7) доходит до браузера как есть, вместе
  с `reason`. Логика реконнекта из п. 7 не меняется.
- Размер кадра: на gateway поднят лимит до 4 МБ (дефолт Reactor Netty — 64 КБ, и превышение
  означало бы обрыв соединения с кодом `1009`, а не усечение). Со стороны фронта делать
  ничего не нужно, но если увидите `1009` — это сигнал, что кадры выросли ещё сильнее,
  скажите бэкенду.
- Прямое подключение на `:8085` больше не сработает даже изнутри сети: runtime отдаёт `401`,
  если запрос пришёл не через gateway.

Дальше по плану безопасности появится:

- обязательная идентичность на `POST /api/runtime/recipes/apply` (заголовок/токен);
- привязка WS-сессии к пользователю — подключиться к чужому `sessionId` станет нельзя;
- роли: применение уставок будет доступно не всем, нужно уметь скрывать действие и обрабатывать `403`.

## Чек-лист

- [ ] Таймаут `apply` поднят до ≥ 15 с (клиент и прокси), кнопка блокируется до ответа.
- [ ] `sessionId` передаётся в `apply` всегда.
- [ ] Экран результата различает `ok` / `partial` / `error`, показывает `failedRows` и `unmatchedRows`.
- [ ] Булевы строки в редакторе — чекбокс/селект, отправляется `true`/`false`; `value_type` — селект.
- [ ] Существующие наборы проверены на булевы значения вне списка написаний.
- [ ] WS-кадр применяется по порядку массива, батчем; дубли `tagId` внутри кадра не ломают стейт.
- [ ] Нет логики, завязанной на «каждое изменение = отдельный кадр».
- [ ] `properties` и `tags` рендерятся независимо, рассинхрон между ними допустим.
- [ ] Close `1003` не вызывает реконнект; `1006`/`1001` — вызывает, с обновлением токена.
- [ ] Guard от двойного подключения (StrictMode, быстрый реконнект).
- [ ] WS-URL = env-origin + `wsPath` из ответа, без хардкода порта.
- [ ] Origin WS и REST переведён на gateway `:8080` (включая STOMP канала), `?token=` на WS.
- [ ] Есть индикация устаревших значений по `ts`.
- [ ] `DELETE /api/runtime/sessions/{id}` при уходе с экрана мониторинга.
