# Учебная сессия по коду

Ты ведёшь сессию. Четыре остальных скила — исполнители: они делают свою работу и
возвращают результат, а план, нить и журнал держишь ты.

## Перед началом

Прочитай `.claude/learn/METHOD.md` целиком.

## Шаг 1. Свежесть карты

Прочитай шапку `docs/learning/map/MAP.md` и сравни:

```bash
git rev-parse HEAD
git status --porcelain -- gateway/src/main auth/src/main channel/src/main editor/src/main runtime/src/main
```

- **Карты нет вовсе** — скажи, что без карты сессия будет медленной, и предложи
  сперва вызвать `code-map`. Дождись согласия.
- **`snapshot` отстал от `HEAD` или рабочее дерево грязное** — скажи, на сколько
  коммитов отстала карта, и предложи обновить. Отказался — работай по имеющейся, но
  предупреждай на каждом узле, где карта могла соврать.
- **Совпадает** — молча иди дальше. Не отчитывайся о том, что всё в порядке.

## Шаг 2. План сессии

Разбери цель на составляющие сам. Не спрашивай пользователя, какой скил звать — он
для того и пришёл, чтобы этого не решать.

Найди в `FLOWS.md` сценарии, покрывающие тему, и в `modules/*.md` — точки, которые
придётся разобрать отдельно. Покажи план списком и спроси, всё ли в нём нужно:

```
Тема разбивается на два маршрута и три точки:
1. маршрут «ACTION с фронта → скрипт → команда в ПЛК»
2. маршрут «смена тега → on_change»
точки: script/ScriptEngineService, script/OnChangeDispatcher, script/TagWriteSink
Начнём с первого маршрута?
```

Тема на одну сессию не влезает — скажи об этом и предложи, что взять сегодня. Лучше
пройти один маршрут до конца, чем начать три.

## Шаг 3. Ведение

Вызывай исполнителей по обстановке:

| Что нужно | Кого звать |
|---|---|
| маршрут целиком | `code-tour` |
| точка по имени | `code-explain` |
| вопрос «почему так себя ведёт» | `code-investigate` |
| карта устарела | `code-map` |

После каждого вызова верни разговор в план: назови, что закрыли и что осталось.

`code-tour` возвращает строку `маршрут: <название>, узел <N> из <M>, пройдено: …` —
сохраняй её. После отвлечения продолжай с того же узла, а не с начала.

**Исполнители друг друга не вызывают.** Цепочка `tour → explain → tour` идёт через
тебя: `code-tour` вернёт управление, ты зовёшь `code-explain`, потом снова
`code-tour` с указанием узла, на котором остановились.

Следи за уровнем. Пользователь отвечает на проверочные вопросы уверенно и быстро —
не сбавляй глубину, но не разворачивай заново то, что он подтвердил. Ответы
неуверенные — сбавь темп и добавь примеров, а не наоборот.

## Шаг 4. Завершение

Покажи черновик выводов и спроси, согласен ли пользователь с формулировкой. Журнал
должен отражать его понимание, а не твоё изложение.

Затем допиши в `docs/learning/JOURNAL.md` — **только допиши, ничего не перезаписывая**:

```markdown
## ДД.ММ.ГГГГ — <тема сессии>

**Разобрано:** <маршруты и точки списком>

**Выводы:** <что теперь понятно, своими словами — не пересказ кода>

**Открытые вопросы:**
- <вопрос, на который не хватило времени или ответа>

**Задачи в beads:** <id с пояснением в скобках, если что-то завели>
```

Затем пополни `docs/learning/KNOWN.md` — **только теми терминами, на проверочные
вопросы по которым пользователь ответил.** Термин, который просто прозвучал в
объяснении, не добавляй: иначе глоссарий забьётся тем, что пользователь слышал, и
скилы перестанут объяснять нужное.

`JOURNAL.md` и `KNOWN.md` ведёшь только ты. Прямой вызов `code-explain` мимо тебя
записи не оставляет — это осознанная разница между «сесть разбираться» и «спросить
на бегу».
