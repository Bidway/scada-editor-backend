# Метод разбора кода

Общий для скилов `code-study`, `code-map`, `code-tour`, `code-explain`,
`code-investigate`. Единственная копия — не дублируй этот текст в скилы.

## Сначала вопрос

На каждом узле разбора сперва задай вопрос по существу и дождись попытки ответа.
Объяснение идёт только после.

Вопрос должен быть про механику, а не на угадывание названия:

- Хорошо: «что произойдёт с остальными сессиями, если отправка одной зависнет?»
- Хорошо: «как думаешь, почему здесь `tryLock`, а не обычный `lock`?»
- Плохо: «как называется этот паттерн?»
- Плохо: «понятно?»

Если ответ неверный — не поправляй сразу. Спроси, что привело к такому выводу:
неверная догадка показывает, какого куска картины не хватает, и объяснение надо
строить оттуда.

Если пользователь говорит «не знаю» — это нормальный ответ, переходи к объяснению.
Не дави и не повторяй вопрос другими словами.

## Схема разбора точки

Любую точку — класс, метод, поле, кусок конфигурации — разбирай по пяти пунктам
в этом порядке:

1. **Что делает.** Одно предложение, без жаргона.
2. **Кто вызывает и откуда.** Конкретные вызывающие с путями файлов.
3. **В каком потоке исполняется, какое состояние держит.** Если состояние есть —
   кто ещё к нему обращается.
4. **Почему сделано именно так.** Загляни в `git log -p` по файлу: если видно, что
   было раньше и почему поменяли, это самая ценная часть разбора.
5. **Где грабли.** Что сломается при изменении, какие входные данные приведут к
   неожиданному поведению.

Пункт 4 пропускать нельзя. Разбор без «почему» даёт узнавание, а не понимание.

## Уровень объяснения

Базовая планка — **с нуля**. Ни один термин не считается известным заранее.

Новый термин вводится по цепочке:

1. Определение простыми словами.
2. Бытовая аналогия.
3. Пример на конкретных значениях из этого проекта.
4. Проверочный вопрос.

Два жёстких правила:

- **Термин не используется раньше, чем объяснён.** Если в объяснении «пула потоков»
  понадобился «блокирующий вызов» — сперва объясни блокирующий вызов.
- **Пример на реальных значениях из этого кода.** Не «представим, что клиент
  медленный», а «50 сессий, одна висит 2 секунды — остальные 49 ждут те же
  2 секунды».

Образец уровня:

```
ПОТОК — отдельная «рука» программы. Одна рука делает одно дело
за раз; пока занята — всё остальное в ней ждёт.

ПУЛ ПОТОКОВ — заранее нанятая бригада таких рук. Задачу отдают
бригаде, свободная рука берёт. Здесь размер бригады =
runtime.flush-threads.
```

## Источник правды

**Код.** Читай `.java`, `.yml`, `build.gradle.kts`.

Не читай как источник фактов о коде: `docs/`, `README.md`, `CLAUDE.md`. Они
отстали от кода, и пересказ устаревшей документации закрепляет неверную картину.

Javadoc и комментарии внутри исходников читать можно — они часть кода. При
расхождении комментария с кодом верен код, а расхождение стоит завести в beads:
`bd create`.

Каталоги `build/` и `bin/` содержат устаревшие копии ресурсов — исключай их из
любого поиска.

## Глоссарий

`docs/learning/KNOWN.md` хранит термины, уже объяснённые и подтверждённые.

- **Перед объяснением термина** сверься с `KNOWN.md`. Термин там есть — не
  разворачивай заново, максимум напомни одной строкой.
- **Пополняет `KNOWN.md` только `code-study`**, и только после того, как
  пользователь ответил на проверочный вопрос. Прозвучавшее объяснение само по себе
  в глоссарий не попадает: иначе он забьётся тем, что пользователь «слышал».
